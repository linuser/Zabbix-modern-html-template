# Development

The media types are **generated**. Structure, look, colours and texts live in separate source files; `build.py` combines them into one Zabbix media type per language and variant. Nothing generated is committed - GitHub Actions builds the files and attaches them to releases.

## Repository layout

```
build.py                      the build (Jinja2 + CSS inlining + checks + zips)
build.yaml                    build matrix: version, export format, languages, variants, naming
requirements.txt              Python dependencies of build.py

src/
  messages.yaml               the 10 message templates: rows, theme, button, subject
  themes.yaml                 colours - Zabbix severity palette and event-type themes
  i18n/<lang>.yaml            texts, one file per language
  css/base.css                CSS shared by all flavours (dark mode, button, badge)
  templates/
    base.html.j2              page skeleton: <head>, Outlook settings, <style>, preheader
    components.html.j2        macros: row value, severity badge, bulletproof button
    media_type.yaml.j2        the Zabbix YAML export around the rendered messages
  flavors/
    standard/
      message.html.j2         structure of the standard flavour
      style.css               look of the standard flavour
    compact/
      message.html.j2
      style.css
  preview/
    sample.yaml               sample macro values for the previews
    logo.svg                  placeholder logo for previews and the E2E test

docs/img/                     README screenshots - generated by test/e2e/e2e.sh docs
test/e2e/                     Docker end-to-end test, see TESTING.md
.github/workflows/            build.yml (build + release), e2e.yml (end-to-end test)
```

Terminology: a **flavour** is a layout (`src/flavors/<name>/`); a **variant** is a flavour plus options (logo on/off) and becomes one media type (`build.yaml`).

## Building

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python build.py              # dist/yaml/*.yaml + dist/*.zip
.venv/bin/python build.py --preview    # + dist/previews/index.html with sample data
```

Open `dist/previews/index.html` to see every variant with sample data: all six severities, every message type, the *unresolved* state (as sent by the media type Test button) and every language.

The build stops with an error if

- a language misses keys of `en.yaml` or has extra ones,
- a template uses an undefined variable or text key,
- CSS custom properties or template syntax are left in the output,
- a message exceeds 65535 bytes (Zabbix stores templates in a `TEXT` column),
- the written YAML, parsed again, does not contain exactly the rendered messages.

It warns if colour combinations in `src/themes.yaml` fall below WCAG contrast.

## How a message is built

For every variant × language × message:

1. **Render** `src/flavors/<flavor>/message.html.j2` with the message from `messages.yaml`, the texts of the language and the theme colours.
2. **Theme tokens**: in the flavour CSS, `var(--accent)`, `var(--on-accent)`, `var(--ink)` and `var(--tint)` are replaced with the colours of the message's theme.
3. **Inline** the CSS with [css-inline](https://github.com/Stranger6667/css-inline): every rule outside `@media` becomes a `style=""` attribute - Outlook and Gmail need that; `@media` blocks (dark mode, mobile) stay in a `<style>` tag. Write CSS with classes; never write inline styles in templates except for values the template computes.
4. **Severity colours**: `var(--sev-accent, #E45959)` (and `--sev-ink`, `--sev-tint`) become a fallback plus a Zabbix macro function:
   `background-color: #E45959;background-color: {{EVENT.NSEVERITY}.regrepl(^5$,#E45959,^4$,#E97659,…)}`.
   Zabbix resolves the second declaration at send time. If it stays unresolved (Test button) it is invalid CSS and the fallback wins. The patterns are anchored because `regrepl()` applies the pairs one after another - without `^…$` the `4` inside `#E45959` would be replaced by the next pair.
   HTML attributes cannot carry a fallback, so `bgcolor` and the VML `fillcolor` (`theme.attr()` in the templates) get the expression alone. In real notifications they then match the CSS - important for classic Outlook, which may prefer `bgcolor`. In an unresolved Test mail browsers still use the CSS fallback; classic Outlook may show an arbitrary header colour there.
5. **Wrap** all ten messages into `src/templates/media_type.yaml.j2`, parse the YAML again and compare.

Zabbix macros (`{HOST.NAME}`, `{$ZABBIXHOST_LINK}`) are plain text for Jinja and pass through unchanged. Never write `{{`, `{%` or `{#` in templates unless you mean Jinja.

## Common changes

### Change a text

Edit the key in `src/i18n/<lang>.yaml` - in every language.

### Add a language

1. Copy `src/i18n/en.yaml` to `src/i18n/<code>.yaml` (ISO 639-1 code; it also becomes `<html lang>`) and translate the values.
2. Add the code to `languages` in `build.yaml`.

### Add or remove a row

Edit the message in `src/messages.yaml`. A row is `[<text key>, <value>]`; the value is a macro, `{text: <key>}` for a translated text or `{pill: <macro>}` for a severity badge. New text keys must be added to every language.

### Change colours

`src/themes.yaml`. A theme is either static (`accent`, `on-accent`, `ink`, `tint`) or `severity: true` with a `fallback`. The severity palette itself is under `severity.levels`. Rebuild and check the contrast warnings.

### Change a layout

Structure: `src/flavors/<flavor>/message.html.j2`. Look: `src/flavors/<flavor>/style.css`. Shared: `src/css/base.css` and `src/templates/`. Keep e-mail rules in mind: tables for layout, `bgcolor` attributes next to background colours, no CSS variables, flexbox, grid or positioning in the output.

The button sizes are parameters of `ui.button()` in the flavour template, because its VML twin for classic Outlook sits inside a conditional comment where CSS cannot be inlined.

After a visible change, regenerate the README screenshots with `test/e2e/e2e.sh docs` and commit `docs/img/` (see [TESTING.md](TESTING.md#readme-screenshots)).

### Add a flavour

1. Create `src/flavors/<name>/message.html.j2` (extend `templates/base.html.j2`, import `templates/components.html.j2`) and `src/flavors/<name>/style.css`.
2. Add one or more variants with `flavor: <name>` to `build.yaml`.

### Add a variant option

Add the key to the variants in `build.yaml` - every key of a variant is available in the templates as `variant.<key>`; `logo` is also passed as `logo`. Then use it in the flavour templates.

### Support another Zabbix version

`zabbix_version` in `build.yaml` is the export format. Keep it at the **oldest** supported Zabbix version: newer versions convert older export formats on import, so a 7.0 export imports into 7.0, 7.2, 7.4 and later. Raise it only when the templates need a newer feature, and run the end-to-end test against every version you claim (`ZABBIX_TAG=… test/e2e/e2e.sh run`, see [TESTING.md](TESTING.md)).

## Outlook specifics

- Classic Outlook for Windows renders with Microsoft Word: no `border-radius`, `box-shadow`, `max-width`, `rgba()`, CSS background on some elements. Layout therefore uses tables, `bgcolor` attributes and solid colours.
- Buttons use a VML `<v:roundrect>` inside `<!--[if mso]>` plus the normal link inside `<!--[if !mso]><!-->…<!--<![endif]-->`.
- `<html>` declares `xmlns:v` and `xmlns:o`; `<head>` contains the `OfficeDocumentSettings` block (96 dpi) and an Outlook-only font rule.
- Images need a `width` attribute; Outlook ignores CSS widths on images.

## Releasing

1. Set `version` in `build.yaml` (e.g. `1.3`) and update `CHANGELOG.md`. If the look changed, run `test/e2e/e2e.sh docs` and commit `docs/img/`.
2. Merge to `main`.
3. Tag and push: `git tag v1.3.0 && git push origin v1.3.0` (the tag must start with `v<version>`).

`.github/workflows/build.yml` builds, runs all checks and creates a GitHub release with the zips (`all`, one per variant, one per language, previews). Every other push and pull request builds too and uploads the zips as a workflow artifact.

### Trying the automation on a fork

In a fork, GitHub Actions is disabled until you enable it on the fork's *Actions* tab. Then:

- every push to the fork runs the build, and pull requests within the fork run the end-to-end test;
- a test tag creates a release in the fork only - nothing happens upstream:

  ```bash
  git tag v1.2.0-test1 && git push origin v1.2.0-test1     # tag must start with v<version>
  # look at https://github.com/<you>/Zabbix-modern-html-template/releases, then clean up:
  gh release delete v1.2.0-test1 --cleanup-tag --yes
  ```
